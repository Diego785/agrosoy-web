# Decisions

Architecture decision records. Each entry says what was decided and why. When a decision
changes, add a new entry that supersedes the old one instead of rewriting history.

---

## D1 · One web application, organized as a modular monolith

**Decision:** a single Next.js application holds the UI and the server logic, split into
modules (`src/modules/<module>`) with clear boundaries. No separate backend service.

**Why:** one developer, six weeks, one database. A separate API service would double deployment
and wiring work without a user benefit. Module boundaries keep the option of extracting
services later.

## D2 · Clean architecture layers inside each module

**Decision:** every module has four layers, and dependencies only point inward:

| Layer            | Contains                                                                   | May import                     |
| ---------------- | -------------------------------------------------------------------------- | ------------------------------ |
| `domain`         | entities, value objects, business rules; pure TypeScript                   | `shared/domain` only           |
| `application`    | use cases, input schemas (Zod), ports (repository interfaces), permissions | `domain`, `shared/application` |
| `infrastructure` | Drizzle tables, repository implementations, PDF and email adapters         | everything above               |
| `presentation`   | pages' components, server actions, data loaders                            | everything above               |

ESLint enforces the first two rows (`no-restricted-imports`).

**Why:** the rules that matter most (debt, stock, exchange rates) live in code with no framework
in it, so they are tested fast and stay readable. Use cases receive their repositories as
arguments, so the same use case serves the web UI today and a JSON API later.

## D3 · Use cases are the only way to change data

**Decision:** server actions and API handlers do three things: identify the user, call one use
case inside a transaction, translate the result. Use cases always check permissions and validate
their input with Zod, even when the form already did.

**Why:** server actions are public POST endpoints. Hiding a button is not a permission check.

## D4 · PostgreSQL 16 with Drizzle ORM

**Decision:** PostgreSQL 16 (as stated in the proposal) accessed with Drizzle ORM and
`node-postgres`. Migrations are SQL files generated by `drizzle-kit`, committed, and applied by
a small script on deploy.

**Why:** transactions and constraints are what keep stock and debt consistent. Drizzle stays
close to SQL, needs no engine binary on the VPS, and its migrations are plain SQL we can review.

## D5 · Exact money, quantities and exchange rates

**Decision:** value objects `Money` (integer cents), `Quantity` (integer thousandths) and
`ExchangeRate` (four decimals), parsed from decimal strings. Postgres `numeric` columns. Rounding
is half up to the cent, only when converting currencies or multiplying quantity by price.

**Why:** floating point turns 0.1 + 0.2 into 0.30000000000000004; a statement must add up to
the cent.

## D6 · Append-only ledger and kardex; voids are reversals

**Decision:** customer debt is a ledger of entries and stock is a log of movements. Confirmed
documents are never edited or deleted; voiding writes the opposite entries with a reason.

**Why:** the proposal promises that nothing is deleted and every change is traceable. It also
makes the statement and the kardex reproducible at any past date.

## D7 · Stock can never go negative, enforced by the database

**Decision:** a `stock_balances` projection (warehouse × lot) is updated in the same transaction
as each movement, with `CHECK (quantity >= 0)`.

**Why:** two users confirming deliveries of the last units at the same moment must not both
succeed. A constraint is the only check that holds under concurrency.

## D8 · Authentication with Better Auth, sessions in Postgres

**Decision:** Better Auth 1.7 (username and admin plugins) with sessions in our database and
four roles (`admin`, `manager`, `sales_technician`, `warehouse_keeper`).

- No self sign-up. Administration creates accounts; the system generates a temporary password,
  shown once, and the user must replace it at first sign-in (`mustChangePassword`).
- Sign-in and sign-out go through `/api/auth` from the browser, so Better Auth's rate limiting
  applies to password attempts. Everything else uses server actions.
- Accounts are written by our own repository (user row plus a "credential" account with Better
  Auth's scrypt hash) so the change and its audit entry share one transaction.
- Users without email get a placeholder under the reserved `.invalid` domain, never shown.
- Deactivating a user bans it and ends its sessions; nothing is deleted.
- Sessions end after 8 hours without activity (extended every 30 minutes of use).
- Business permissions live in `shared/application/permissions.ts` as defaults per role.
  Administration adjusts them on the permissions page; only the differences are stored
  (`role_permission_overrides`), so new permissions arrive with their default. The `admin` role
  always keeps every permission. Each request loads the effective permissions into the `Actor`.

**Why:** no third-party identity provider to pay for or depend on; users are a handful of staff.

## D9 · Next.js 16 rendering: Cache Components on, financial data never cached

**Decision:** keep `cacheComponents` and `partialPrefetching` (the Next.js 16.4 defaults). Page
chrome prerenders; anything that reads the session or the database renders inside `<Suspense>`
at request time. `"use cache"` is not used for balances, stock or statements.

**Why:** fast navigation without ever showing a stale debt or stock figure.

## D10 · Server Actions for the UI, route handlers for files and the future API

**Decision:** forms call server actions that return a typed `ActionResult`. PDFs, Excel exports
and the future mobile API (`/api/v1`) are route handlers that call the same use cases.

**Why:** the proposal commits to an internal API reusable by a later offline mobile app.

## D11 · UI: Tailwind CSS and shadcn/ui, Spanish text, one locale

**Decision:** Tailwind CSS 4 and shadcn/ui components in `shared/presentation/ui`. The app has
one locale (`es-BO`), so Spanish text lives in the components; error codes from the domain are
translated in one place (`shared/presentation/error-messages.ts`). Responsive down to phone
width, because technicians and keepers work from their phones.

**Why:** an i18n library adds indirection with no second language to serve.

## D12 · Documents: PDFs generated on the server

**Decision:** delivery notes, receipts and statements are rendered to PDF on the server and
shared with the phone's share button (WhatsApp included). Library to be chosen in week 3 after a
spike: `@react-pdf/renderer` (lighter) or HTML printed by headless Chromium (closer to the screen).

**Why:** automatic WhatsApp sending needs a paid service and is out of scope.

## D13 · Testing pyramid

**Decision:** Vitest unit tests for every domain rule; integration tests that run use cases
against a real Postgres test database (`*.int.test.ts`); a few Playwright end-to-end tests for
the critical flows (deliver, collect, statement) before go-live. CI runs all of them on every
pull request.

**Why:** the costly bugs here are wrong balances, and only a real database shows how
constraints, transactions and rounding behave together.

## D14 · Hosting on the SolutionTech VPS with Docker

**Decision:** the app runs as a Docker image (`output: "standalone"`) next to Postgres on the
VPS. Two environments: `staging` (weekly demos) and `production` (Agrosoil's subdomain). Daily
`pg_dump` copied off the server, 30 days kept. GitHub Actions builds the image after a push to
`main`; the server pulls it.

The VPS is a borrowed server that already runs a shared nginx with certbot for other projects. So
instead of the Caddy first planned, each environment publishes no ports: it joins the shared Docker
network and nginx proxies to it by container name, with one `.conf` file of ours
(deploy/README.md). Until the domain is decided, staging is reached by IP and port.

**Why:** the proposal promises this setup, and it keeps hosting cost at the Bs 50/month quoted. A
second proxy on ports 80/443 isn't possible on that server, and following its conventions keeps our
changes inside our own folder and file.

## D15 · Language and time

**Decision:** code, identifiers, comments, docs and commits in English; user-facing text in
Spanish (Bolivia). Business dates and reports in `America/La_Paz`.

## D16 · Git workflow

**Decision:** each week is built on a `feature/week-N` branch, in roadmap order, and every commit
leaves it working (`pnpm check` passes locally, CI on every push to any branch). `main` keeps the
version of the last demo and receives the week's branch once the developer approves it. No pull
requests while one developer works on the project. Conventional commit messages. Commits are authored by the developer only: no `Co-Authored-By`
or tool attribution lines.

## D17 · Imported spreadsheets live apart from the system's records

**Decision:** an uploaded spreadsheet is stored as an import batch (`import_batches` and its
lines, summary rows and findings), never as delivery notes, payments or ledger entries. Importing
the same sheet and campaign again replaces its batch. Conversion into real records is a separate,
reviewed step of M12.

**Why:** the spreadsheets have known inconsistencies (missing exchange rates, formulas that skip
rows, reused note numbers). Keeping them apart lets Agrosoil review and correct them, and lets the
statement preview show real figures in week 1 without polluting the ledger that M5–M7 will build.

## D18 · Notes are confirmed before inventory exists

**Decision:** in week 3, confirming a delivery note gives its number and posts the ledger, but takes
no stock. When inventory (M8) arrives in week 4, the same confirm use case also writes the stock
movements in its transaction, and warehouse and lot become required on new notes.

**Why:** the week 3 milestone is notes, collections and statements with real data; inventory is
week 4. Go-live stock comes from a physical count (`opening` movements), so notes confirmed before
then never needed a stock movement.

## D19 · One number sequence for notes, given on confirmation

**Decision:** delivery, return and campaign-transfer notes share one gapless counter
(`document_counters`, row-locked while a number is taken). Drafts have no number. Administration
sets where numbering continues; paper notes typed in later keep their printed number, which must
be unused, and the counter skips numbers already taken. Receipts get their own counter.

**Why:** Agrosoil uses one paper pad today (open question in the glossary; if the types turn out to
have separate pads, the counter gets one row per type). Numbering at confirmation means discarded
drafts leave no gaps.

## D20 · Payments are applied per campaign, oldest debt first by default

**Decision:** a payment becomes one ledger credit per campaign it pays (`payment_allocations`).
Administration may apply it to one note (recorded on the allocation, credited in the note's
campaign) or to one campaign; otherwise campaigns that owe are paid oldest first. An overpayment
stays as a credit in favor in the payment date's campaign. Cash notes create their payment while
they are confirmed, in the same transaction, for exactly the note's total.

**Why:** debt is followed per campaign (the statement and the spreadsheets are organized that way),
and "oldest first" is how administration applies an unspecified payment today. Keeping the
allocation rows makes every credit traceable to its receipt.

## D21 · PDFs with @react-pdf/renderer (completes D12)

**Decision:** notes, receipts and customer statements are PDFs drawn with `@react-pdf/renderer`
in route handlers (`/notes/[id]/pdf`, `/payments/[id]/pdf`, `/statements/[customerId]/pdf`) that
call the same use cases as the pages. The pages offer "PDF" and "Compartir": the latter hands the
file to the phone's share sheet (WhatsApp included) where the browser supports sharing files.
Text only, Helvetica, until Agrosoil provides its logo.

**Why:** it renders in the Node server already in the Docker image, with no headless browser to
install or keep patched on the VPS, and Next.js already treats it as an external server package.

## D22 · Spreadsheet sales become imported notes; undated payments become ledger entries

**Decision:** converting a sheet's sales creates confirmed delivery notes marked `imported`, with
the sheet's note number in `sheet_number` (the system's `number` stays empty), and posts their
debt. The summary's payments and returns, which have no document and no date, are posted as
ledger entries whose source is the import batch, dated on a cut-off date administration chooses.
No payment records or receipts are invented. A converted sheet can't be re-imported until the
conversion is undone, which voids the notes and reverses the entries.

**Why:** the sheets reuse note numbers on different dates and their pads overlap the numbering
the system continues (D19), so imported numbers can't share the unique column. Inventing dates,
payment methods or receipt numbers would put false facts in the ledger; a dated cut-off entry is
honest and still reconciles to the cent. Undo keeps the ledger append-only (D6) while letting
administration fix a sheet and convert it again before go-live.

## D23 · Product codes belong to presentations and keep Agrosoil's numbers

**Decision:** a code identifies a presentation (a product in one container), as in Agrosoil's
product list: "001" is Fulvin 40-22 in 20 L, "002" the same product in 5 L. Codes are text of three
or more digits, unique, imported as written; a new presentation takes the next free number. The
product groups its presentations by name. Products and presentations no longer sold are
deactivated, never deleted, so old documents keep them. A catalog import reads Agrosoil's list (name
with the container in brackets, US$ price, price unit) into a preview to review before saving;
its prices become the campaign's general reference prices (no zone), which each zone can override.
Presentations can be counted in units (a bag of 50 sheets); a listed product without a container
is created as "1 unit, priced per container" and flagged for administration.

Importing the list again applies what changed, by code: a code in use with the same container
updates that presentation's price for the chosen campaign, and renames its product when every
presentation of it in the list carries the new name (not when only some do, nor when another
product already has the name). The preview shows each price before and after, and each rename.
A code in use with another container, or a container the product already has under another code,
is still left out. A new presentation proposes the next free code in the form, and it can be
changed.

**Why:** staff, paper notes and price lists already use these codes, one per container. New
numbers would force everyone to relearn them, and a product-level code can't tell a 1 L bottle from
a 20 L can.

## D24 · Charges have a concept, and a price adjustment can lower the debt

**Decision:** the "OTROS" codes of Agrosoil's product list are charge concepts, not products: 079
interest, 080 price adjustment, 081 notarized contracts, plus "other". Administration enters a
charge with its concept and a reason, in an open campaign. Interest and notarized contracts are
debits; a price adjustment can be a debit or a credit. Charges never touch stock and are voided,
never deleted.

**Why:** it answers the open question on interest (they charge it). The list mixes these concepts
with products because the spreadsheets bill them as rows, but in this system a product takes stock.

## D25 · Returns and campaign transfers gather lines from several deliveries

**Decision:** a return or campaign-transfer note lists lines from any confirmed delivery notes of
the same customer and campaign. Each line keeps its link to the delivered line it gives back or
moves, which fixes its price and limits it to what is still consigned. The note itself no longer
points to a single original note; its PDF lists the deliveries it draws from.

**Why:** the paper form has no "original note" field, and one return slip can bring back product
from several deliveries. With one printed number it has to be one note.

## D26 · Notes and receipts print like Agrosoil's paper forms

**Decision:** the PDFs follow the forms Agrosoil uses (photos of 28 Oct 2026).

- **Note:** one layout for the three types, with the type's box checked (entrega, devolución,
  traspaso). Header: date, customer with NIT or CI, property ("Hac."), cash or credit, campaign.
  Columns: quantity, description, presentation, total liters/kilos, unit price US$, total US$.
  Footer: total in US$ and Bs with the exchange rate, observations, carrier (company, vehicle, CI),
  the person who hands over and the one who receives (names, position, CI; signed on paper).
- **Receipt:** amount in its currency (Bs or US$) and in words, "received from", concept (built
  from what the payment was applied to, editable), on account / balance / total (D27), place and
  long date ("Santa Cruz, 28 de octubre de 2026"), and two signatures with name and CI.
- Document numbers print with six digits (012951).

Notes get optional carrier fields and a "handed over by" person: the technician by default (the
warehouse keeper once inventory exists); on a return the customer's person hands over and
Agrosoil's receives. Users get an optional position ("Ejecutivo de ventas") and CI to print them.
The company's name, logo and contact details come from a settings page; the documents carry the
brand printed on the forms, **Agrosoil Bolivia**.

**Why:** customers and staff already know and sign these forms; the printed copy stays the
physical record, so it must look like the one they trust.

## D27 · A receipt keeps the balances of the moment it was issued

**Decision:** recording a payment stores the customer's balance (US$) right before and right after
it. The receipt prints them as total, on account (the payment) and balance. Reprints and later
payments don't change them; voiding the payment marks the receipt as void.

**Why:** a receipt is evidence of one moment. Recomputing would make two prints of the same
receipt disagree.

## D28 · Paper pads and the system number in separate ranges

**Decision:** paper notes and receipts typed in later keep their printed numbers (receipts can now
take one too). Numbers the system gives start in a range the pads won't reach, set by
administration per document (for example from 100001). A number is unique across both, whatever
its origin. Completes D19: the counter is the same, it only starts elsewhere.

**Why:** technicians keep using pads in the field, often without signal, while the system issues
documents. A counter that continued the pad would collide with its next sheet.

## D29 · Agrosoil enters its own opening debts; spreadsheets are optional

**Decision:** going live doesn't depend on Agrosoil sharing its sales spreadsheets. Administration
enters, from a chosen **cut-off date** (the day the system starts):

- an **opening balance** per customer and campaign (amount, date, note) for debt without detail;
- **historical notes**: paper notes typed with their printed number, date and lines, only where
  product is still on consignment and may be returned or carried over;
- **historical payments** with their printed receipt number;
- customers and the product list through imports with a preview, matched by normalized name.

Notes dated before the cut-off never move stock; a return dated after it does, because the product
physically comes back. The spreadsheet import and its conversion (D17, D22) remain an optional tool
that Agrosoil can run on its own sheets.

**Why:** Agrosoil can't share the full sales spreadsheets; the sample it sent shows the format, not
the data. Entered inside their own system, the data stays theirs. Typing every old note would be
too much work; only consigned product needs its lines.

## D30 · Travel allowances follow Agrosoil's weekly expense report

**Decision:** M10 is a **weekly expense report** per technician, modeled on Agrosoil's spreadsheet
(`10. VIATICO OCTUBRE 2026.xlsx`):

- Header: week (Monday to Saturday), technician, position, zone of work.
- Expenses, in bolivianos, by category: fuel (with odometer reading), lodging, food (per day),
  tolls, entertainment (with a description), vehicle maintenance and repairs, vehicle accessories,
  other. Each has date, amount, invoice control code, observation and an optional receipt photo.
  Vehicle costs say who paid: the technician (from the allowance) or Agrosoil directly.
- Subtotal minus the **cash advanced** gives what is reimbursed or returned.
- States: draft → submitted (technician) → approved (management) → paid (administration), like the
  form's signatures "Ing. / Aprobado / Revisado y cancelado".
- A **monthly limit** per technician (Bs 4,800 by default) with its difference, and **vehicles**
  with their person in charge, whose maintenance and accessories add up per month.
- PDFs and reports: the weekly form for signing, the monthly summary per category and the monthly
  cost per vehicle (the spreadsheet's hidden sheets).

**Why:** it is how Agrosoil already accounts for field expenses, including approvals and the limit,
so the module replaces the spreadsheet instead of running beside it.

## D31 · Every visit to a screen starts clean

**Decision:** with Cache Components, Next.js keeps the last screens mounted but hidden (React
Activity), so a form comes back with what was typed, or with what was just saved. Forms are wrapped
in `resetOnLeave` (`shared/presentation/reset-on-leave.tsx`), which mounts them again when their
screen is hidden; it covers the browser's back button too. Filter forms are keyed by the search they
show, so they always show the filter applied to the list. Components whose initial state comes from
stored data (the price sheet, a product's name) are also keyed by that data, so they start again
when it changes elsewhere. Dates are typed and shown as dd/mm/aaaa (`DateInput`) whatever the
browser's language, with the browser's calendar behind a button; amounts, quantities and codes
select their whole value when tapped (`selectOnFocus`).

**Why:** Agrosoil's staff expect a new note or product to start empty and a list to show what its
filters say; a half-typed draft left on a hidden screen is more likely a mistake than work to keep.
